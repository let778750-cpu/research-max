# 返工、补丁与重写

本文件回答：卡住之后，怎么判断该继续修、该换手段，还是该重来。核心判据：**有没有定位到根因，而不是已经改了几次。**

## 一、补丁堆叠的识别清单

出现其中两条以上，说明已经进入堆补丁，应停下排查而不是继续加：

- 同一个函数里出现第三个"如果是某种情况就……"的分支。
- 用 try/catch、默认值或空实现包住来源不明的失败。
- 加超时、加重试、加轮询来掩盖不稳定，而不是解释不稳定。
- 为单个用例写特判，且没有对应的一般规则。
- 参数或开关持续增殖，每加一个都是为了绕开上一次的问题。
- 测试里出现跳过、放宽断言、改期望值。
- 注释开始写"这里为什么要绕过"，而不是"这里为什么这样设计"。

清单的作用是触发诊断，不是自动否决；有时确实需要兼容分支，但要说清它对应哪条真实约束。

## 二、根因诊断顺序

固定四步，不要跳步：

1. **复现**：用最小输入稳定复现，记录命令与输入。
2. **定位**：读数据流、日志、中间量，指出"哪一行的哪个值不该是它"。
3. **一次改动**：只改定位到的那一处，写清预期改变哪个观测。
4. **同一路径复验**：用同一复现路径验证，不换新用例掩盖。

反模式是"改→跑全套→看是否绿"。全套测试通过只说明没被现有断言抓住，不说明根因已定位。

## 三、回滚点

- 动手前记录可回滚状态：版本号、快照、备份路径或可复现的初始命令。
- 回滚后要验证确实回到已知状态，而不是"应该回去了"。
- 回滚是止损手段，不是失败记录；回滚原因与回滚点写进检查点。

没有回滚点的多步改动，等于每一步都在加不可逆的风险。

## 四、重写计价

重写、换框架、换技术栈之前，四项都要有：

| 项 | 要写什么 | 不合格的样子 |
|---|---|---|
| 旧方案的失败证据 | 具体现象、复现路径、已排除的原因 | "感觉架构不好" |
| 新方案省掉的迭代 | 预计少走哪几步、依据是什么 | "重写会更干净" |
| 迁移与重学成本 | 要改的文件、要重跑的实验、要重新理解的部分 | 只算写新代码的时间 |
| 结论 | 做／不做／先做局部替换 | 直接开工 |

三项缺一就不做。探索期的一次性原型不受此限，但要记放弃理由，避免同一路线被反复重写。

## 五、维护成本估算

重写或重构前，用四个问题估维护成本：

1. 改一处典型需求，要动几个文件？
2. 有没有隐式依赖（全局状态、约定、顺序）？
3. 下次接手的人需要读多少才能改？
4. 现有测试会不会因结构变化而失效，要不要重写？

四个问题里有两个答不上来，说明还没到能重写的理解程度。

## 六、反例

- 用"重写更干净"作为唯一理由。
- 没定位就重写，结果旧缺陷在新结构里复现。
- 重写后不保留旧方案的失败证据，下次又走一遍。
- 把回滚当成丢脸，硬着头皮继续堆。
- 把"两次停手"理解成"两次就必须放弃"：停手是停下来诊断或换手段，不是宣布问题无解。
