# 项目侧 AGENTS.md：模板与逐节解读

research-max 是方法库：它规定怎么做研究，不知道你的项目状态、数据在哪、验收口径是什么。项目侧 AGENTS.md 只补这三件事，并把“什么任务读哪个技能”写成路由。两者分工固定：常驻文件放原则与路由（建议 80—120 行），方法细则留在技能内。

## 文件

| 文件 | 用途 |
|---|---|
| [AGENTS.md](AGENTS.md) | 复制到项目根目录改名为 `AGENTS.md`；含占位符，复制后替换并删除文件头注释 |
| README.md | 本文件：逐节解读、搭配方式、反例 |

## 逐节解读

| 节 | 解决什么 | 细则由谁提供 |
|---|---|---|
| 项目入口与规则分工 | 读哪几个文件；任务状态只有一个入口；代码、文献、案例、归档各放哪；沿用哪个状态后端 | 项目自己 |
| research-max 按任务路由 | 什么任务读哪个 SKILL.md，用到哪一步为止，哪些动作不自动授权 | 本仓库各技能 |
| 逐轮汇报 | 每轮交付怎么讲：判断、证据、边界、强度、缩写 | turn-report 技能的 T1—T7 |
| 投入与止损 | 多轮任务怎么开工、先摆几条路线、卡住几次停手、何时收缩或重写、汇报带哪些成本账 | effort-guard 技能的 E1—E9 |
| 独立判断与研究讨论 | 不附和、先机制后创新、近邻命中的处置、范围交代 | research-topic 技能 |
| 研究与验收 | 基线、对照、真值与仿真分离、工程自检与科学 Gate 分级 | research-execution 技能 |
| 渐进推进、记录与规范维护 | AGENTS、PLAN、TASKS 的分工；证据绑定；目录维护 | research-execution 技能 |
| 项目硬边界 | 数据落盘、凭据与隐私、外部动作授权、被测系统与评价器分离 | 项目自己 |

## 搭配方式（三步）

1. 复制模板到项目根目录，替换 `<项目名>`、`<README>`、`<TASKS>`、`<代码目录>`、`<案例目录>`、`<归档目录>`、`<已有后端或“无”>` 等占位符；把 `<research-max>` 换成本地克隆的绝对或相对路径。模板刻意不写死路径，换机器只需改一处。
2. 保留路由表的结构，按项目实际删减行；要加任务类型就加一行，不把 SKILL.md 的正文搬进来。
3. 项目可配置值（模型与执行团队、预算与重复、引用与字数、版式、图件载体、图中文字等）写进项目配置或“项目硬边界”，未知填 null，不继承任何来源项目取值。

## 与技能的分工（一句话版）

- 项目 AGENTS 回答“这个项目读什么、听谁的、做完怎么交代”。
- 技能回答“这类任务按什么步骤、什么判据做”。
- 冲突时以项目 AGENTS 的项目事实（目录、状态源、授权）为准，以技能的方法判据为准；两者都不覆盖用户的当轮目标。

## 反例

- 把 SKILL.md 正文抄进项目 AGENTS：同一规则两处维护，必然漂移。
- 在项目 AGENTS 里重写论文格式与统计规范：那属于 paper-writing 与 research-execution。
- 写死技能版本号、本机绝对路径或某次实验的数值：换机器、换批次即失效。
- 用“测试通过”冒充“科学结论成立”，或用同一个模型换角色冒充独立复核。
- 把所有技能都写成“默认加载”：常驻上下文变长，反而更容易漏读当前任务需要的那一份。
- 把“投入与止损”的三格写成审批关卡：填表是为了让成本可见，不是为了多一道许可。
- 用“以后难维护”否掉尚未试过的新方向：维护闸不能前置到没有证据的阶段。

## 与仓库根 AGENTS.md 的关系

仓库根的 `AGENTS.md` 是 research-max 自身的维护约定（单一维护、跨技能不链接、来源登记、离线脚本不联网等），不适用于你的项目，也不要复制进项目。本目录的模板才是项目侧文件；它随仓库分发，但不参与本仓库的维护判断。
