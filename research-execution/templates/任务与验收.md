# 任务合同与验收记录

## 单任务正文

- ID、阶段、目的、负责人：
- 上游任务；输入文件、版本及适用范围：
- 可写目录；保护对象；预计资源：
- 最小实施步骤与输出文件：
- 验收条件：数值、分母、边界、反例、物理或测量依据。
- 自检方法；需要非作者复核的内容：
- 失败返回哪个问题；阻断项及可独立继续的工作：

`tasks.json`是状态源。每项任务采用项目骨架中的字段，`outputs`记录实际产物的相对路径与SHA256。开始工作时填写`owner`；进入REVIEW后保留自检证据；通过实质复核再写ACCEPTED。

## 工具消费的验收结构

任务中的文件引用使用如下结构，尖括号文本是待替换说明，不能作为有效证据：

```json
{"path": "reviews/G2.json", "sha256": "<文件的64位SHA256>"}
```

需要独立复核的任务，其`review`引用的JSON采用：

```json
{
  "task_id": "G2",
  "verdict": "ACCEPT",
  "reviewer": "<实际复核者>",
  "independent_context": true,
  "artifact_sha256": {"artifacts/G2-report.md": "<产物SHA256>"},
  "checks": ["<实际检查的方法、反例、结果和定位>"],
  "limitations": ["<尚未覆盖的范围；没有则空数组>"],
  "context_record": "<复核者实际获得的材料及独立性依据>"
}
```

`artifact_sha256`与本次任务全部输出一一对应。复核文件的哈希再写入任务的`review`字段。工具检查绑定及声明完整性，不认证人员身份、独立上下文或科研判断。

无需独立复核的低风险任务可将`review_required`设为false，在`self_check`中记录实际检查。不能为绕过科研核心复核而临时关闭该字段。

## 退回与历史

`history`追加时间、旧状态、新状态、原因及旧证据位置。产物变化后重新验收，下游依赖重新评估；不覆盖旧回执。在BLOCKED时写`blocked_reason`，DEFERRED时写`defer_reason`，二者都不计完成。
