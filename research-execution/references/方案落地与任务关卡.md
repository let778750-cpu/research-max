# 研究方案如何落实为实施推进

## 先把方案变成合同

将每条假设拆成可观测变量、必要输入、竞争解释、对照、主指标、失败条件和资源需求。然后沿证据依赖拆任务：来源是否可靠先于算法成绩，评分正确先于方法比较，基线成立先于新机制归因。不要按“找文献、写代码、画图”三个笼统任务直接开跑。

每项任务至少写：目的、输入、依赖、唯一负责人、写入范围、输出位置、内容验收条件、复核方式、失败后的去向。任务量以能形成一次有意义的证据交付为准；不强制一段代码一个任务，也不把一整篇论文塞进一个不可检查的任务。

| 方案表述 | 可执行任务 | 验收证据 |
|---|---|---|
| 改善识别 | 固定输入与评分，比较基线和一个最小新增机制 | 原始预测、计数、效应及误修正 |
| 有泛化能力 | 明确未见对象、时间、设备、条件或场景层级 | 分组隔离、开发信息范围、冻结及留出结果 |
| 数据充分 | 核验字段、标签、有效独立组和误差来源 | 数据卡、缺口与样本规模依据 |
| 有效率优势 | 核算模型、工具、人工与链路开销 | 同约束比较、费用账及端到端测量 |
| 可解释 | 明确解释是否有独立根因真值 | 证据一致性、根因评分或限定的案例分析 |

模板见[任务与验收](../templates/任务与验收.md)。

## 从完整计划拆到短期模块

总体计划保留目标、范围、设计依据、阶段依赖与最终验收；每项任务注明对应的计划条目，整体交付时逐项核对覆盖和必要集成结果。阶段出口不能由局部任务完成数替代。

沿证据依赖划分能够独立检查、独立退回的模块；若一部分已可验收、另一部分仍需返工，就考虑拆开。准备、实现和必要验证围绕同一个产出组织，不机械地一条命令一任务。近期模块写到可执行，依赖未知结果的远期模块先写目标、前提与展开条件，随证据细化；不提前编造实验步骤或冻结未知参数。

G0—G9 是科研阶段，短期模块是阶段内工作。阶段关卡依赖必要模块，模块依赖上一阶段或真实输入，不依赖自己的阶段出口。分组归属与先后依赖分开，避免形成环。范围已缩小的项目按实际任务保留相关阶段，不为每个阶段堆占位文件。

## Markdown 权威记录与状态标签

默认以总体计划 PLAN.md 和任务推进 TASKS.md 分工；已有短计划可直接加入任务区，不强制拆文件。较长说明、实验日志和复核另存 Markdown 并链接。**每项任务的当前状态只在选定任务文件维护一次**；README、总体计划和交接只导航到它，不手抄另一份实时状态。JSON 不是必需载体；旧项目可继续以既有 tasks.json 为权威，但同一项目不能双写。

“断点”指模块任务状态标签，用于人和其他模型检查与接续，不表示暂停执行或逐项审批。状态采用：

| 标签 | 含义 |
|---|---|
| 待做 | 尚未开始，依赖是否满足另行判断 |
| 进行中 | 已开始，说明实际完成部分与剩余工作 |
| 待核验 | 已提交实际产物和自检，等待所需验收 |
| 已验收 | 指定版本满足本任务验收条件，不自动证明科学假设成立 |
| 受阻 | 缺少必要输入或外部条件，写明阻断范围、原因与解除条件 |
| 暂缓 | 当前范围暂不推进，写明原因及承接关系，不计完成 |

兼容工具内部状态 TODO/RUNNING/REVIEW/ACCEPTED/BLOCKED/DEFERRED，与上表一一对应。复核退回重进“进行中”，保留原因与旧回执。没有独立复核者时留在“待核验”或明确自检范围。负结果、排除解释或确定不可复现原因可以是合格交付，步骤勾选不能自动升级任务状态。

选择下一任务先查依赖、输入版本和验收证据；一个依赖受阻时，其他确实独立且已授权的工作继续。模块产物改变时评估受影响下游；旧验收仍绑定旧版本，不覆盖历史造成假连续。必要检查未通过前不进入依赖该证据的正式运行。

模块取得实质进展、提交核验、发现阻碍、调整计划或交接时，更新任务卡中的当前进展与下一步。写清“实际做了什么、依据在哪、还缺什么、下一步具体做什么”，不逐次工具调用填表，不反复播报无变化状态。普通更新后持续执行，真正涉及范围、预算或外部动作的决定按已有授权处理。

阅读和修改不依赖工具。需要机械检查时，为 ID、状态、依赖、责任、复核、版本与承接关系使用少量字段约定，其余内容保持自然段与列表，详见[Markdown任务格式](Markdown任务格式.md)。可选汇总从权威 Markdown 生成，须标明派生与源版本；过期或读取失败不能显示成完成。Markdown 结构错误和 JSON 格式合法都不决定科学正确，模板只提供最小检查入口。

## 任务身份与承接

同一交付目标仅补步骤或调整实现时保留ID；目标实质改变、新增独立产出时新建ID。ID不复用、不全盘重编号。输入或验收条件改变而交付目标仍相同时，可以沿用ID并更新要求版本，保留变更理由和旧证据。计划变化的完整同步流程由[证据反馈](证据反馈与变更控制.md#计划调整后同步任务)维护。

| 变动 | 当前任务如何维护 |
|---|---|
| 调整顺序或前置条件 | 修改依赖与下一步，核对已经运行或验收的下游 |
| 拆分 | 新卡承接可独立验收部分；旧卡明确已完成范围和转交内容。若旧卡继续做集成验收，更新其要求并依赖子任务，不把子任务产出再计成一次交付 |
| 合并或替代 | 新卡写合并后的目标与条件；退出原执行职责的旧卡登记承接任务，不把旧验收自动继承给新卡 |
| 退出本轮 | 未完成旧卡设为暂缓，原因写明本轮取消或被谁替代，不自动恢复；旧卡已有合格产出则保留其原范围验收，不改写成新目标已完成 |

“承接任务”只用于已经移交原执行职责的旧卡，可一对多或多对一；不是依赖，不自动传递验收。当前仍需执行的集成父任务使用依赖关系。历史卡不删除；依赖仍指向已移交旧卡时明确核对需要的是旧范围证据还是新产出。六种执行状态保持不变，拆分、替代和取消写关系及原因，不增设一组并行状态。

原成果在新条件下仍适用时保留验收并按需记依据；需要补核验时使用待核验（已有实际产物和自检），需要返工时进入进行中，缺少必要前置证据时受阻；尚未开始的任务继续待做。已验收产物在新范围中是否适用，与历史验收当时是否成立分别表达。

## 验收强度与风险匹配

科学核心包括数据准入、评分、物理或测量实现、正式协议、主要统计及主张，安排非作者实质复核。没有独立复核者时保留REVIEW或明确自检完成，不把自己换个角色名写成独立评审。轻微文字与布局修改可自行复查，不需要人为制造多代理关卡。

验收绑定实际产物、哈希、当时任务要求、检查内容、反例、复核身份与结论。任务要求改变，即使产物字节未变，也须重新判断适用性；不能只刷新回执哈希或复制新版本号冒充复核。不同身份字符串不能证明独立上下文；哈希校验也不判断复核质量。每个阶段允许带有**明确不影响当前退出条件**的待办，但须指定承接任务、影响范围和最晚解决时点；阻断项不能靠写“非阻断”转移。

## 设计接受、冻结和交付分别记录

方案获得认可，表示可以按范围开展开发，不等于所有参数已锁定。正式冻结要等数据、原理、基线与小试证据齐备。稿件完成、科学主张成立、投稿材料齐全和已正式提交是不同状态。

小试证明某机制没有增量信息时，先修机制或数据；停止该分支并报告负结果也是有效推进。不能靠增加提示词、重复审计或堆管理文件假装解决科学问题。

## 模块粒度与外部执行

任务是验收单位；采用GitHub记录时，交付模块可以包含一张或几张任务卡，不再建立重复的父任务卡。四项共同支持时适合归组：能用一句具体的话说明共同产出；围绕同一接口/方法经常共同修改；主要检查可共享且逐项覆盖；一起集成、修回或回退自然。只因同一阶段、相同文件/模型/数据，不足以合并。不按任务数、代码行数或时长设固定阈值。

示例：评分实现、手算边界核验和单位说明可交付同一个可信评分器；评分核验与正式效果比较应保留证据关卡；可独立使用的启动工具不必等待长时间扫描才交付。随机种子一般是运行实例，无须各建任务或分支。新任务若本就过细，合成一张卡内的步骤；已有执行与证据则保留稳定ID，仅在交付层归组。

同一轮交付内成员不可重复归属，归组不能制造依赖环（如T-1→T-2→T-3时将T-1与T-3包成必须先整体完成的模块）。成员部分完成不能整组通过；拆出可独立交付部分须保留未完成项与承接关系。机械检查只验证结构，不能判断共同目标是否有研究意义。具体可选发布流程见[GitHub模块记录](GitHub模块记录.md)。

任务边界以可独立检查、退回或决定下一步的产出为准。简单关联工作合并，内部步骤用列表；不用函数、文件、工具调用数或固定时长制造任务。评分核验与效果比较因证据依赖而分开，必要集成检查不能因各模块已完成而省略。外部执行的启用与交接仅在用户指定时按[跨Harness任务执行](跨Harness任务执行.md)处理，不增加所有项目的填写负担。
