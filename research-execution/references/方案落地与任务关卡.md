# 研究方案如何落实为实施推进

## 先把方案变成合同

将每条假设拆成可观测变量、必要输入、竞争解释、对照、主指标、失败条件和资源需求。然后沿证据依赖拆任务：来源是否可靠先于算法成绩，评分正确先于方法比较，基线成立先于新机制归因。不要按“找文献、写代码、画图”三个笼统任务直接开跑。

每项任务至少写：目的、输入、依赖、唯一负责人、写入范围、输出位置、内容验收条件、复核方式、失败后的去向。任务量以能形成一次有意义的证据交付为准；不强制一段代码一个任务，也不把一整篇论文塞进一个不可检查的任务。

| 方案表述 | 可执行任务 | 验收证据 |
|---|---|---|
| 改善识别 | 固定输入与评分，比较基线和一个最小新增机制 | 原始预测、计数、效应及误修正 |
| 有泛化能力 | 明确未见对象、时间、设备、条件或场景层级 | 分组隔离、开发信息范围、冻结及留出结果 |
| 数据充分 | 核验字段、标签、有效独立组和误差来源 | 数据卡、缺口与样本规模依据 |
| 有效率优势 | 核算模型、工具、人工与链路开销 | 同约束比较、费用账及端到端测量 |
| 可解释 | 明确解释是否有独立根因真值 | 证据一致性、根因评分或限定的案例分析 |

模板见[任务与验收](../templates/任务与验收.md)。

## 单一状态源与工作队列

`tasks.json`是唯一任务状态源，Markdown任务表若需要应自动生成。`project.json`记录阶段、范围与关键入口；README提供导航，不能替代实时状态。

采用`TODO → RUNNING → REVIEW → ACCEPTED`。缺必要输入或外部条件时用`BLOCKED`；决定不在当前范围做则用`DEFERRED`，均不计完成。复核退回后重进RUNNING，保留原因及旧回执。上游产物变化时核对受影响下游，旧验收仍对应旧哈希，不覆盖历史造成假连续。

选择下一任务时，先检查依赖与输入有效性；能独立推进的工作继续，不因一个依赖阻塞全部研究。无法证明依赖满足时不进入正式运行。每次实质进展汇报“完成了什么证据、发现了什么、下一步解决什么”，不持续播报无变化的状态。

## 验收强度与风险匹配

科学核心包括数据准入、评分、物理或测量实现、正式协议、主要统计及主张，安排非作者实质复核。没有独立复核者时保留REVIEW或明确自检完成，不把自己换个角色名写成独立评审。轻微文字与布局修改可自行复查，不需要人为制造多代理关卡。

验收绑定实际产物、哈希、检查内容、反例、复核身份与结论。不同身份字符串不能证明独立上下文；哈希校验也不判断复核质量。每个阶段允许带有**明确不影响当前退出条件**的待办，但须指定承接任务、影响范围和最晚解决时点；阻断项不能靠写“非阻断”转移。

## 设计接受、冻结和交付分别记录

方案获得认可，表示可以按范围开展开发，不等于所有参数已锁定。正式冻结要等数据、原理、基线与小试证据齐备。稿件完成、科学主张成立、投稿材料齐全和已正式提交是不同状态。

小试证明某机制没有增量信息时，先修机制或数据；停止该分支并报告负结果也是有效推进。不能靠增加提示词、重复审计或堆管理文件假装解决科学问题。
