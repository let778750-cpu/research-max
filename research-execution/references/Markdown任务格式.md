# Markdown 任务与工具格式

仅在使用本地检查、汇总或快照工具时需要此约定。拆分与验收原则见[方案落地与任务关卡](方案落地与任务关卡.md)；日常阅读、修改和接续无需运行工具。

## 可选GitHub记录与模块分组

仅启用GitHub记录的项目使用[接入模板](../templates/GitHub记录接入.md)。`## GitHub记录约定`和`## 模块分组`放在任务卡之外，不使用`## M-001 ...`来伪装另一种任务。约定恰含仓库、指定任务、授权来源、当前接手者、发布、合并方式、基线分支七项；模板说明列出取值。模块表四列固定为模块、任务、共同产出、集成条件；不含状态列。成员用顿号/逗号分隔，模块ID用M-前缀；单元格不使用嵌套表格或竖线。

check自动检查可选分组的重复ID、成员存在性、唯一归属与归组后的依赖环，board展示派生成员状态；二者不联网、不判断GitHub合并情况。未启用项目无需添加字段。分组规划可以先有模块表而没有发布约定，不因此开启外部操作。任务要求摘要不绑定这两节；分组调整本身不废弃科学验收，但GitHub合并封存另行绑定本轮分组与成员要求。

## 任务卡的固定字段

以 `## T-003 模块名称` 开始任务。ID 以英文字母开头，包含至少一位数字，只含英文字母、数字、下划线或连字符，项目内唯一；G0、T-003 都合法。其余一级、二级标题为普通文档结构。任务的三级章节可以自由补充。

在任务标题后、首个三级章节前，用以下顶层列表填写控制字段。支持中文/英文冒号，字段不重复，不用粗体包装字段名；说明文字放进三级章节。

| 字段 | 写法与何时需要 |
|---|---|
| 状态 | 必填：待做、进行中、待核验、已验收、受阻、暂缓，六选一 |
| 依赖 | 必填：任务 ID，用顿号或逗号分隔；没有则写“无” |
| 复核方式 | 必填：独立复核或自检；科学核心沿用非作者实质复核要求 |
| 负责人 | 开始执行前填写实际负责人，待做时可不填 |
| 对应计划 | 计划条目或实际 Markdown 链接；实质检查核对覆盖关系 |
| 阶段 | 可选，阶段归属不自动成为依赖 |
| 复核记录 | 绑定回执时填写：`[回执](reviews/T-003.md) | 64位SHA256` |
| 要求版本 | 新模板使用 V1，任务要求实质改变时递增；旧记录未启用时明确兼容提示 |
| 自检依据 | 版本化任务提交待核验或低风险自检验收时填写：`V1 | 64位要求摘要` |
| 承接任务 | 仅旧卡移交执行职责时添加承接 ID，用顿号或逗号分隔；没有则省略 |

普通章节不需要键值结构。工具读取 `### 实施与验收条件`（或 `### 验收条件`）的非空正文/列表；`### 当前进展与下一步` 用于汇总；`### 自检记录` 保存实际自检；受阻和暂缓分别使用 `### 阻断原因`、`### 暂缓原因`。其他章节如目标、输入、写域、步骤和变更记录保留自然语言，不作机械语义判定。步骤复选框不改变状态。

待做可保留空白；进行中须有负责人、真实验收条件及已验收的必要依赖。待核验须有实际产物及自检；已验收还须满足指定的自检或独立复核要求。占位词不是有效证据。普通进展无需哈希，进入待核验或验收时才绑定实际文件。

## 产物与复核

在 `### 产物与证据` 下使用两列表格，格式示例：

```markdown
| 产物 | SHA256 |
|---|---|
| [结果](artifacts/result.md) | <该文件的64位SHA256> |
```

尖括号值不可用于验收。空白模板不预填产物或通过结论。未来输出写路径文字，链接与表格登记已存在的材料。

独立复核用[验收记录模板](../templates/验收记录.md)。字段为任务、结论（通过/退回）、复核者、复核方式（独立复核/自检）、独立上下文（是/否）。正文包括检查内容、产物与证据、上下文依据和局限。通过记录的产物及 SHA256 须与任务本次全部产物对应；任务再绑定回执文件的哈希。低风险任务可直接在任务卡的自检记录写实际检查。身份字符串和“是”只是声明，不证明独立性。

版本化任务的回执还填写 `- 验收依据：V1 | 64位要求摘要`。任务卡的自检依据绑定实际自检，回执的验收依据绑定实际复核；两者不能代替产物版本绑定。

Markdown 链接相对**所在文件**解析；子目录回执可用 `../artifacts/result.md`，最终目标须在项目内。含空格或括号的路径用 `[名称](<相对路径>)`。本地 Markdown 锚点也检查；证据哈希绑定整个文件，不接受章节锚点或远程 URL。网页链接保留但不联网验证。机器读取的引用使用行内链接，不使用引用式链接、标题属性或嵌套链接。

围栏代码、引用块、缩进代码和 HTML 注释中的示例不会成为任务。不要把真实任务放在这些区域；不支持任意 Markdown 方言。无法识别时报告问题，不猜测为完成。

## 计划修订与验收依据

采用分开的计划与任务文件时，在文件开头、首个二级标题之前填写文档控制字段。格式示例：

```markdown
# 总体计划
- 当前修订：R2
```

```markdown
# 任务推进
- 计划文件：[总体计划](PLAN.md)
- 已同步计划修订：R2
```

计划文件路径相对任务文件，可在项目内子目录；须指向整个本地 Markdown 文件。合并为一个计划/任务文件时只写 `当前修订`，不再写计划文件和已同步修订。修订写作 R正整数、要求版本写作 V正整数，字段不重复。计划的变更条目可放在“重要调整”下使用三级标题，避免 `## C-003 名称` 被当成任务标题。

`check` 发现两份修订不同会报告未同步，`board` 显示诊断而非成功标题，`snapshot` 不创建新快照；这不是暂停其他独立工作的指令。同步编号相同只代表声明一致，内容覆盖仍按[计划同步流程](证据反馈与变更控制.md#计划调整后同步任务)核对。

要求摘要由 `basis` 只读计算，覆盖：任务 ID、要求版本、`目标与边界` 正文、可选 `输入与版本` 正文、验收条件、依赖 ID 和复核方式。不覆盖计划整体、负责人、任务标题、实施步骤、状态、进度、自检正文、变更历史或产物；产物有独立 SHA256 绑定。关键输入须在正文明确版本或摘要，工具不追踪链接文件的隐含变化，也不理解自然语言适用性。这些要求章节内的代码块、引用和注释也纳入内容绑定，但其中的示例标题不会成为额外任务；改变进度章节中的代码或例子不影响要求摘要。

新模板将“实施步骤”和“验收条件”分开；旧“实施与验收条件”仍支持，但其整段都参与要求摘要。空行/排版等可能造成保守失配，实质未变时核对后记录沿用依据，不能盲目刷新摘要。真实要求改变时更新 V编号并重新判断旧产物适用性；即使忘记递增编号，正文摘要改变也会拒绝旧回执。仅改进度或计划其他模块不使本任务回执失效。

提交前运行 `basis --task <ID>`，实际核验后将返回的版本与摘要填入自检依据或复核回执，再对回执文件计算哈希。计算摘要本身不会改文件或证明检查发生；不应由工具自动替换旧回执中的依据。旧回执保留在变更记录引用，不重新签名伪装为新验收。

承接任务检查存在性、重复、自指及环，与依赖图分开检查；承接不自动解锁下游。旧卡须为暂缓或原范围已验收，集成父任务请使用依赖。工具提示仍指向旧卡的依赖，由实际证据判断是否需要重接。历史任务卡保留在同一任务源中，不复制到第二份可编辑状态账。

未启用这些字段的旧项目继续可用，诊断与汇总会说明未覆盖计划修订或任务要求绑定。新增字段后须完整填写；不能删除版本字段来规避已采用的新要求。首次采用时先核实旧记录，再填写依据，不批量将历史验收认证为当前有效。

## 命令与兼容

使用 check、board、snapshot 需要项目内的 project.json 配置，可由 init 生成或按项目骨架填写；它保存项目与快照前置配置，不是第二份任务状态账。basis 及人工阅读、编辑 Markdown 不要求这个配置文件。

以下从本技能目录运行，项目路径由当前使用者指定：

```text
python scripts/research_infra.py init --dest <空目录> --name <名称>
python scripts/research_infra.py init --dest <另一个空目录> --name <名称> --task-format json
python scripts/research_infra.py check --root <项目>
python scripts/research_infra.py check --root <项目> --tasks protocol/实施计划.md
python scripts/research_infra.py hash --root <项目> --files artifacts/result.md reviews/T-003.md
python scripts/research_infra.py basis --root <项目> --task T-003
python scripts/research_infra.py board --root <项目>
python scripts/research_infra.py board --root <项目> --output artifacts/推进概览.md
python scripts/research_infra.py check --root <项目> --board artifacts/推进概览.md
python scripts/research_infra.py snapshot --root <项目> --id <快照ID> --kind protocol --files <明确文件>
python scripts/research_infra.py verify --root <项目> --manifest snapshots/<快照ID>.json
```

默认查找项目根 TASKS.md 或 tasks.json，只能有一个。自定义文件或双源时，给 check/board/snapshot 显式传 `--tasks <项目相对路径>`，并在项目入口说明权威选择。工具不猜优先级、不自动迁移、不双写，不缓存另一份任务账。旧 JSON 字段及回执继续兼容。

`basis` 同样支持 `--tasks`；省略 `--task` 时计算所有版本化任务，空白目标/验收条件不能生成提交依据。修订同步尚未完成时可先计算局部要求摘要，但这不解除 check 的不一致诊断。

兼容保留字段与命令，不保留漏检：两种格式的待核验任务均须有产物和实际自检；空检查、占位负责人或占位验收条件不能通过。已有不完整记录可能因此报错，修补证据即可，无需迁移格式。

`board` 默认只打印 Markdown，指定输出才保存只读派生概览；只覆盖本工具生成的概览，不覆盖人工文档、任务源或已登记证据。阅读旧导出前可用 `check --board` 检查源摘要和内容是否过期。检查出错时概览只展示记录标签，不构成有效验收。`hash` 只计算显式文件摘要，不改状态。

其余命令返回 JSON 诊断；退出码 0=所检查机械项通过，1=发现不一致，2=输入/读取错误。JSON 诊断和快照是工具产物，不是任务权威记录。snapshot 保持明确列出文件、阶段前置条件和只创建不覆盖规则。

## 旧 JSON 项目的填写参考

仅供已有 JSON 项目或显式选用兼容模式时使用。字段全集见[旧任务空白骨架](../templates/兼容/tasks.json)。状态仍为 TODO、RUNNING、REVIEW、ACCEPTED、BLOCKED、DEFERRED。文件证据使用 `{"path": "artifacts/result.md", "sha256": "<64位摘要>"}`，路径相对项目根。

下面是旧独立回执的**格式示例**，不是通过记录；尖括号内容须替换为实际证据后才可使用：

```json
{
  "task_id": "T-001",
  "verdict": "ACCEPT",
  "reviewer": "<实际非作者复核者>",
  "independent_context": true,
  "artifact_sha256": {"artifacts/result.md": "<产物64位SHA256>"},
  "checks": ["<实际检查方法、结果、反例与定位>"],
  "limitations": [],
  "context_record": "<实际获得的材料与独立性依据>"
}
```

任务 `review` 绑定回执本身的路径和哈希，`artifact_sha256` 对应本次全部产物。低风险任务使用 `review_required: false` 与实际 `self_check`。变更历史保存在 `history`，阻断与暂缓原因分别是 `blocked_reason` 与 `defer_reason`。这些是旧项目的兼容写法，不要求 Markdown 项目维护同名字段或副本。

JSON 可显式采用同一组新检查：任务源顶层 `plan` 为 `{"path":"PLAN.md","revision":"R1"}`；任务增加 `requirements_version`、`goal`、可选文字 `inputs`，用 `self_check_basis` 保存 `{"version":"V1","sha256":"<要求摘要>"}`，用 `successors` 保存承接 ID 列表；回执使用同形的 `requirements_basis`。同一内容的字段值相同即可计算同一摘要，JSON 无须维护 Markdown 任务副本。
