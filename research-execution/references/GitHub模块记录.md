# GitHub 模块记录（可选）

仅当用户指定某个项目或任务范围采用 GitHub 记录并开始执行时使用。确认实验方案、打开旧仓库、查询进度和加载本技能都不启动发布。该能力与跨 Harness 执行独立：可以由当前 Codex 完成，也可在用户另行指定时由 Claude Code 执行。已明确的范围内，提交、必要修回、既有审核和合并连续推进，不逐模块询问许可。记录文件是授权来源的索引，不能替代当前会话中的真实用户授权。

## 分工与唯一状态

计划 Markdown 保存研究目标与调整；任务 Markdown 保存唯一可编辑的任务状态、要求版本和验收依据。一个置顶进度 Issue 展示生成的总览；一轮模块实施对应一个分支和 PR；main 累积已验收且完成集成的产物。任务是验收单位，模块是交付组织单位，分组原则见[方案落地与任务关卡](方案落地与任务关卡.md#模块粒度与外部执行)。

任务状态仍为原六种。总览分别展示任务标签与 GitHub 的草稿/待合并/已合并/关闭未合并，不手填一组模块状态，也不从 Issue/PR 反向覆盖任务正文。记录中的“已验收、尚未合并”是有效情况。读取失败、部分完成、超时、关闭 PR 均不能变成已完成。

运行中由同一个 Codex 主持者维护权威工作区；执行者工作副本中的计划、任务只作输入。main 的同名文件是最近合并版本；总览链接当前已发布的任务快照和提交，标明更新时间。它不是实时终端，不因没有新日志推断运行已结束。新接手者先读总览指向的任务快照，再核对本地权威文件、运行占用和远端事实；仅查看不会自动接管。

## 首次接入

使用[GitHub接入模板](../templates/GitHub记录接入.md)，在权威任务文件的任务卡之外补充可选约定和分组表。未知仓库或执行范围必须先明确，不依据当前目录名称猜测。不要给未启用项目铺满字段；模板是空白材料，不是自动启动命令。

1. 读现有计划、任务、要求版本、进度、产物及占用；已有记录不重新认证。确定本批范围、私有 owner/repo、基线分支、当前接手者和发布方式。
2. 保留已有未提交/已暂存修改，仅发布明确文件。工具不 stash、reset、强推或清理他人工作区。原工作区被其他窗口占用时不切分支，先接续已确认的控制者或选用明确授权的独立工作区。
3. 创建新仓库须明确提供目标并选择创建；已有仓库核对远端及权限后接入。现有历史不重写；新远端接收已有未发布历史须另行核对范围，不能把“只选几个文件”当成历史也只包含这些文件。
4. 发布初始计划与任务基线，建立一个置顶总览，首页链接到它。原始数据、权重和大型运行文件用外部位置、版本及摘要引用；只提交必要小型证据。原始桥接事件、凭据和本机配置不直接发布。

库顶层 integrations/github 提供可选本机 Git/GitHub CLI 组件；具体命令及恢复边界在该组件 README.md 单一维护。research_infra.py 仍离线，原 JSON 项目不批量迁移。若已有仓库要求所有基线变更走 PR，初始化记录也遵守其规则，不绕过保护或修改既有策略。

## 每轮模块实施

**开始：**从最新已合并基线建立 codex/ 前缀分支，先提交实际启动记录，再创建 Draft PR。主持者按真实准备或执行进展更新任务卡，明确区分“正在准备模块”和“GLM 已启动”。不要为了建 PR 虚报运行。

**执行：**复用既有派发、自检、审核及修回。简单步骤可在一张任务卡内完成；已有多个任务可以共享 PR，仍逐项覆盖其验收条件。当前 Claude 桥接一次派发一张任务卡，不为共用 PR 改写这一接口，也不跳过科学上游依赖。现有检查能同时覆盖几个任务时只运行一次，分别链接适用依据。

**记录：**在启动、形成可检查产物、提交核验、阻碍、范围调整、验收和合并时更新。一次提交对应有意义的变化，不按每次工具调用提交。PR 自动引用目标、成员任务、要求版本、当前进展和证据；不复制完整任务正文或聊天历史。运行控制信息不成为另一份可编辑状态账。

**发布安全点：**由 Codex 统一提交、推送和合并；GLM 不操作远端。桥接仍占用项目时，发布器拒绝改写文件或切换分支，等待执行回执/明确停止后的交接点。创建好模块分支后再准备外部执行副本；该副本必须继续满足现有桥接的隔离和版本绑定要求。

## 审核、封存与合并

PR 只记录已有审核，默认不增加模型轮次或人工 Approve，也不安装另一套 AI reviewer。模块验证来自任务的真实验收与必要集成检查。复用仍适用且版本匹配的证据，简单任务不因此重跑全套测试。

主持者完成现有审查后，引用已有验收/检查文件封存提交、基线、模块要求摘要和证据哈希。封存是机械记录，没有新一轮审核；不要求另写 PR 审核报告。集成条件已由任务核验覆盖时，在原检查记录说明覆盖范围即可。文件哈希、命令参数和身份声明不能认证科学正确或真实独立性。

合并前必须满足：必要成员已验收，版本和证据有效，必要集成检查已实际完成，当前提交就是受审版本。工具拒绝缺失封存、审查后变更、尚未集成的新基线和无关分支历史。默认 merge commit，遵守仓库保护要求，不使用管理权限绕过。可信负结果可以交付，合并不表示科学假设成立。

工具核对远端实际合并提交及其父提交/内容后才放行后继模块。GitHub 合并接口能匹配 PR 头提交，但不能原子锁定目标基线；若并发修改导致实际合并版本不同，记录“远端已合并、集成未核实”，停止依赖它的推进，由主持者针对实际差异复核，不悄悄回滚他人修改。现有 CI/保护要求仍需满足；不为记录功能强行新增全量实验流水线。

## 调整与接续

未合并时在原分支修回。合并后修改使用最新 main 上的新轮次分支，关联旧 PR；模块与任务身份稳定，分支随一轮实施结束。首版不自动删除分支或工作副本，避免干扰其他会话；“结束”指不再复用旧分支。

分组或要求变化，保留旧启动记录与提交，按[证据反馈与变更控制](证据反馈与变更控制.md)同步实际影响。单纯重新分组不自动使科学验收失效，但合并封存须重新绑定当前模块范围；科学要求或产物变化仍按原规则局部重验。部分完成不能整组通过，拆出可独立交付部分时保留未完成项和承接关系。

记录层首版串行集成；一轮未结束先接续或明确关闭它，不创建层层堆叠 PR。其他正常讨论及不依赖其集成的已授权工作可继续。范围外依赖不会因分组自动进入执行授权。

网络、推送或响应丢失只产生同步缺口，不重启模型或昂贵实验。恢复先读明确的模块/轮次记录，查询远端 Issue、PR 和提交，再补缺失步骤。已执行的创建/合并不盲目重试；已有最终合并结果优先核实。状态查询是只读能力，发布暂停时仍可使用。用户指定范围完成后结束本批发布，不扩展到整个项目。
